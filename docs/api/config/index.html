Client configuration #

The MTProto API has multiple configuration parameters that can be fetched with the appropriate methods.¶

Machine-readable configuration index #

Unlike the client-side and MTProto configuration parameters described below (which are fetched at runtime with help.getAppConfig and help.getConfig), the API also relies on a number of API constants: sets of identifiers and enumerated values that are not returned by help.getAppConfig or help.getConfig, but are instead hardcoded into official clients and change from layer to layer.¶

Examples include client configuration key names, Premium features and limits, business features, suggested actions, incoming web events, webPage type values and more. Because these constants are tied to the schema, any change to them is documented in the per-layer changelogs on the layers page ».¶

For programmatic access, an aggregated machine-readable index of the current layer of the API is published at the permalink /api/config.json.¶

The endpoint is a single JSON object whose top-level keys each embed, as native JSON, the corresponding dataset of the latest layer:¶

  • layer – the current API layer » number that all the datasets below belong to.
  • constants – the aggregated API constants described in this article, whose shape is documented below.
  • push, push_arguments – the schemas of the push notification service messages », and their localization arguments.

Make sure to also consider the following configuration files which are not included in config.json, and are instead available as separate files:¶

  • The full RPC error database in /api/errors.json, documented here ».
  • The TL schema » of the current layer in /schema/json.
  • The end-to-end encryption schema » in /schema/end-to-end-json.
  • The end-to-end encrypted group call schema ».
  • The schemas and map of the file reference database ».

API constants #

The constants object is keyed by a globally-unique section name – a human-readable identifier for each list of API constants (for example premium features, basic suggestions or webpage type).¶

Each value is an object describing that section, with three keys:¶

  • description – the human-readable description of the section as a whole.
  • type – either map or list, indicating the shape of entries below, so consumers can distinguish the two shapes without inspecting the JSON type of entries.
  • entries – the list of API constants in the section, whose shape matches type:
    • when type is map, an object keyed by the entry identifier (the string constant, e.g. message_length_max, telegram_nft, double_limits__channels), whose value is the human-readable description of that entry (a markdown string).
    • when type is list, an array of the bare entry identifiers (plain strings), for sections whose entries don't carry individual descriptions.

For example:¶

{
    "layer": 225,
    "constants": {
        "webpage type": {
            "description": "Web page type values from the [webPage](https://core.telegram.org/constructor/webPage) constructor.",
            "type": "map",
            "entries": {
                "telegram_nft": "Preview of a collectible gift link.",
                "video": "Preview of an external video."
            }
        },
        "settings paths": {
            "description": "In-app settings deep link paths openable via [settings deep links »](https://core.telegram.org/api/links#settings-links).",
            "type": "list",
            "entries": [
                "appearance",
                "appearance/themes",
                "appearance/wallpapers"
            ]
        }
    }
}

help.getAppConfig#61e3f854 hash:int = help.AppConfig;

The help.getAppConfig method returns a JSON object containing rapidly evolving, client-specific configuration parameters.
While help.getConfig returns MTProto-specific configuration with information about server-side limitations and other MTProto-related information, help.getAppConfig returns configuration parameters useful for graphical Telegram clients.¶

When first invoking help.getAppConfig, pass 0 to hash; in future calls, use the hash contained in the previously returned help.appConfig; if the configuration hasn't changed, a help.appConfigNotModified will be returned instead of help.appConfig.¶

The configuration should be manually refreshed immediately upon receival of an updateConfig update.¶

If any of the configuration keys are not available at runtime, a default value must be used.
Specifically, the relative value from the default object must be used if help.getAppConfig was invoked successfully but the desired key is not available in help.appConfig.config, or if the invocation of help.getAppConfig returned an RPC error and there is no cached value.¶

help.getCountriesList can be used to fetch a list of localized names for all available countries and phone code patterns for logging in.¶

The phone code pattern should be used when showing the login screen, or when changing phone number: for example, a pattern value of XXX XXX XXX with country_code +39 indicates that the phone field for login should accept a spaced pattern like +39 123 456 789.
Also, the beginning of the national part of the phone number (123 456 789) should match one of the prefixes, if any were returned.¶

Additionally, the fragment_prefixes client configuration parameter contains a list of phone number prefixes for anonymous Fragment phone numbers.¶
